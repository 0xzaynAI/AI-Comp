## 五、进化沉淀

### 5.1 核心教训：网络/DNS 故障的「短暂→持续性」识别

上周我把 09-20 的网络故障判断为「短暂、自愈」。**这个判断错了，而且错得隐蔽。** 正确的识别信号是：

- `Last run ... error ... (N failures in a row)` —— cron list 里的「N failures in a row」是持续性故障的铁证，比单次 error 严重得多
- **飞书 delivery 也失败** —— 网络故障的特征是「生成 + 推送」双失败；stream stall 只影响生成、不影响推送
- **连续多天、同一时段失败** —— 09-25/26/27 连续 3 天失败 = 基础设施问题，不是偶发抖动

**教训：任何「短暂故障」都要在下一周验证是否复发。复发 = 升级为「持续性基础设施问题」，需要老板决策（换网络/DNS/机器），而不是继续修代码。**

### 5.2 核心教训：Steve 自动推进的「硬触发器」是假的

上周我写了 3 个硬触发器（「周一 09-21 14:00 前做上架包」等），本周 0/3 落空。根因不是懒，是**结构性的**：

**「在周报里写下一个时间点」≠「设定了触发器」。** 真正的触发器需要一个 cron 在那个时间点叫醒 Steve 去执行。我写下的时间点没有任何调度机制，所以永远不会响。

**教训：Steve 的任何「自动推进」承诺，必须同时注册一个对应的 cron 任务。没有 cron 的承诺，就是周报里的空话。** 这是本周最深刻的自我批评。

- **技能已 patch**：`weekly-evolution-review` 新增「网络/DNS 故障『短暂→持续性』识别信号」+「Steve 自动推进硬触发器必须是真 cron」两条记录。
